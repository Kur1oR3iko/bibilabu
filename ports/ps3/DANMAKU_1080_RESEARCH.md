# PS3 弹幕与 1080p 可行性评估

日期：2026-11-06。依据当前 1.7.0 源码、现有 PSL1GHT SDK 和已保存的 Movian PS3 后端参考源码。以下是工程判断，不是新增功能的实机通过报告。

## 结论

两者都有可行路径。建议先完成少量透明弹幕的 RSX 合成验证，再做 YUV 视频输出/转色，最后按受限片源开放 1080p24/30。不要仅把尺寸上限改成 1920×1080，也不要直接引入整套 OpenGL/Vulkan 界面框架。

当前已经有 CID、音频硬件消耗时钟、暂停状态和索引跳转，可供弹幕计时使用；现有 RSX 输出能在 1080p 显示模式运行，但这不等于已经实现 1080p 视频解码。

## 弹幕的数据与调度

- 可研究 B 站 `x/v2/dm/web/seg.so?type=1&oid=<cid>&segment_index=<n>` 的分段 protobuf 响应，按通常六分钟一段加载。需要独立的有界 protobuf 解析，不能送入当前 JSON 解析器；不能把未知模式的内容当作脚本执行。
- 首版只支持普通滚动、顶部/底部文字，限制同屏约 6–8 条、每条长度、缓存总量与字形数量。高级/定位/BAS 模式暂不处理。
- 使用视频公开的播放时间（seek 基准 + 硬件已消耗音频样本），暂停时冻结，跳转时清空活动队列并重定位。不要使用独立累积的系统时间，否则暂停与跳转后会错位。
- 下载和解析放在低优先级工作线程，使用取消与代际检查；暂停/退出时不得等待无限网络操作。媒体供给和音频优先于弹幕预取。

## 透明渲染的两条路线

现有程序使用 RSX transfer/scale，把主内存 ARGB 图像复制到显存。当前 operation 是 `SRCCOPY`，仅有不透明 OSD；直接在黑底文字矩形上“画弹幕”会挡住视频。

SDK 的 `gcm_sys.h` 确实定义了 `GCM_TRANSFER_OPERATION_BLEND_AND` 和 `GCM_TRANSFER_OPERATION_BLEND_PREMULT`。因此可以先验证预乘 ARGB 文字位图的小规模 2D 混合：确认透明像素、文字边缘、缩放、源/目标内存位置和 GPU fence 都正确。存在枚举不代表现有状态配置下开关一改就能用，必须实机确认。

如果 2D 混合不足以满足效果或性能，再使用原生 RSX 纹理四边形、字形图集及 alpha blending。字体只在缓存缺字时光栅化，逐帧只更新位置；不能重新引入 CPU 全屏混合和显存读取。字形图集可以主要占用 VRAM，评论文本及布局仍占主内存。

## 1080p 片源边界

优先目标为 H.264/AVC、8-bit、4:2:0、逐行、24/25/30 fps。典型 coded size 是 1920×1088，visible size 为 1920×1080。

Movian 的 [PS3 VDEC 后端](https://github.com/andoma/movian/blob/master/src/arch/ps3/ps3_vdec.c) 对 1088 编码高度且参考帧超过 4 的流禁用硬件加速，对 720 高度的限制是超过 9 个参考帧。这是重要的兼容性参考，不能只看“1080p”标签。仍要检查 profile、level、参考帧/DPB、帧率、码率、裁切、SAR 和实际固件行为。

1080p60、HEVC、AV1、High10 不属于建议的第一阶段。四个视频 SPU 是当前配置，不能未经测量把六个可用 SPU 全部分给视频而忽略音频和其他并行任务。

## 内存及带宽预算

主内存与 VRAM 必须分别预算。下面是外部视频帧池的计算，不包含固件内部 DPB/工作区：

| 格式 | 单帧原始数据 | 10 个输出槽的规划空间 |
|---|---:|---:|
| 1280×720 ARGB | 3,686,400 字节 | 约 40 MiB（现有 1 MiB 步长对齐） |
| 1920×1088 ARGB | 8,355,840 字节 | 约 80 MiB |
| 1920×1088 YUV420 | 3,133,440 字节，另计 plane pitch/对齐 | 约 30–40 MiB |

还要叠加固件查询的视频工作区（实机 Level 4.x 日志约 57 MB）、压缩包队列约 16 MiB、视频输入约 4 MiB、AAC/PCM、UI 两块画布、字体、TLS、JSON 和线程栈。ARGB 路线在 1080p 下明显挤压主内存余量。

推荐 `VDEC_PICFMT_YUV420P` 输出，由 RSX 完成 BT.601/BT.709 转色和缩放。1080p ARGB 每秒 30 帧约 251 MB 的图像数据，YUV420 约 94 MB；这不是实测吞吐，但说明少搬运数据的收益。还应评估将图像纹理放在 VRAM，参考 Movian 的做法；不能把 VRAM 当成普通 CURL/JSON 堆直接使用。

## 当前工具链的实际限制

`/opt/wiliwili-ps3/ps3dev/bin/cgcomp` 的 Cg 前端仍提示缺少运行库，但进一步检查源码并实测确认：`-a` 汇编路径不加载该库。1.8.0 已用此路径生成自有 YUV 转色和透明贴图程序，并校验指令/采样器与矩阵。因而当前项目的这些程序不再被 Cg 前端阻塞，也没有分发第三方编译着色器二进制。

1.8.0 已实现 YUV 与透明控制层，但仍待 PS3 实机验证；弹幕和 1080p 不随之自动开放。

## 建议的实机验收顺序

1. 在现有视频上叠加两行静态透明文字，再滚动至 6–8 条；测音频是否欠载、画面帧率、退出与 GPU fence。
2. 720p 下切换 ARGB 与 YUV 输出，对比颜色、裁切、SAR、同步、内存和帧时间。
3. 只开放满足上述约束的 1080p24/30 测试片源，连续播放、暂停、跳转、换片至少十次，确认内存回收。
4. 达标后再把支持档位加入实际清晰度菜单，并加入带密度上限的弹幕开关。

1.7.0 仍以现有 AVC ≤720p 播放路径为准，不提前暴露未验证的 1080p 选项。
