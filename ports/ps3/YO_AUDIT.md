# Yo! Player 到开放 SDK 的适配记录

参考版本固定为 `UPSTREAM.json` 中的提交。参考源码在本地 `.reference/yo`，不作为本项目的已移植运行库。

| 位置 | 上游行为 | 本项目当前处理 |
|---|---|---|
| `libs/simple-lib-av/src/decode-h264.c` | `cellVdecQueryAttrEx`、`cellVdecOpenEx`、4 SPU、异步回调 | 开放 SDK 只有基础 vdec 声明；扩展 ABI 与绑定待补，不猜参数实机调用 |
| `libs/simple-lib-av/src/decode-aac.c` | `cellAdecQueryAttr/Open/StartSeq`、异步 PCM | 当前开放 SDK 的 codec 目录无 AAC 头；需从公开定义整理 ABI 和导入绑定 |
| `libs/simple-lib-av/src/video-player.c` | 分离音视频流、音频时钟、YUV 帧及分配器回调 | 后续播放器后端设计参考；尚未链接 |
| `libs/simple-lib-av/include/h264.h` | 真实 coded size 与显示尺寸分开处理 | 已成为选流之后必须执行的预探测关口 |
| `apps/yo-player/src/main.c` | 显式进程参数、RTC/VFS/网络/TLS，再图形、音频、字体、输入 | 新启动程序显式提供进程参数并尽早落日志；完整应用初始化后续逐项接入 |

## 格式处理需要先审计

当前上游 `h264.c` 的 `readUe()` 在截断输入导致前导零达到 32 时，表达式 `1u << zeros`
存在移位宽度等于类型位宽的未定义行为。不能因为上游报告实机可播，就省略恶意或截断媒体的边界处理。
这一实现尚未并入当前运行路径。后续复用时需要先收紧 bit-reader 的 EOF、Exp-Golomb 上限和尺寸计算。

## 明确的能力边界

- 选中 H.264 元数据不等于已经验证 8-bit、4:2:0、coded size、参考帧数和解码缓冲大小。
- 参考播放器报告的 720p/1080p 性能不是本机 4.93 HEN 的测量结果。
- HTTP 媒体请求还需保留 B站所需的请求头、重定向和 Range 行为；当前没有实际联网请求或登录。
- Borealis/NanoVG 的 PS3 绘制路径独立于解码层，当前尚未实现。

## 0.4 基础 vdec 诊断路径

新代码独立实现开放 SDK 基础 vdecQueryAttr/Open、异步 AU/PICOUT、ARGB 取帧和退出排空。
未复制 Cell SDK 头或二进制，未直接链接 Yo 解码器。沿用送帧与取帧交替、
输入缓冲保持有效的协议思路。只对合成的 320x240 Baseline Level2.0 单参考帧短片启用。

PPU32 回调描述符通过 SDK 的 __build_opd32 显式创建；编译时断言公开 vdec 结构的大小及关键偏移。
时间戳的固件布局为 upper/lower 两个 32 位字；当前 SDK 的 low/hi 命名需按偏移解释。
该布局与基础类型定义可交叉核对公开的 RPCS3 cellVdec.h；参考文件仅用于 ABI 核对，
没有随程序复制模拟器实现。

0.4 暂不添加 AAC 导入，先以实机确认基础视频模块、回调 ABI 和输出。
AAC 后续独立验证，不能把现有无声短片路径当成完整音视频后端。

## 0.5 480p 性能测试

原生接口继续使用基础 vdec 和 4 SPU 配置，未强行占满所有 SPU。
视频固定为 848x480 Baseline Level3.1、单参考帧、30fps、180帧。
固件输出 ARGB 到 2MB RSX 映射主存；CPU 做缓存写回和同步，RSX 执行缩放 blit。
显示缓冲仍在显存，应用图形仅更新静态页及低频状态文字。
GPU blit 后等待 idle/backend label，输出映射保留到进程结束；不释放可能仍被 GPU 使用的源。
该 RSX 路径、480p 吞吐和完整退出都需要本机实测，不能从 0.4 成功推断。

## 0.6 AAC 与音频时钟

新增自写的公开固件 wire ABI 声明与 MIT PSL1GHT 导入模板适配，未复制 Cell SDK 头或二进制。
AAC 回调 SEQDONE=3/ERROR=2，与视频接口不同；结构大小/偏移有 PPU 编译断言。
生成的ADTS为AAC-LC双声道48kHz，283个AU；原生解码后只对本素材裁剪1024个编码延迟样本，
保留288000个PCM样本。该延迟经主机参考解码脉冲/静音窗核对，不泛化到任意AAC。

为首轮声音验证先预解码约2.3MB PCM，而非直接复制Yo的流式音频混音器。
声音通过独立PPU线程服务32块音频环，按已消费块推进视频；每块256样本、约5.33ms。
首次与恢复使用4块静音预填，对齐以音频源样本进度为准。音频在第一张实际视频画面提交后启动。
仍需要实机检查libadec模块、PCM格式、端口读索引行为、暂停重开端口和完整清理。

0.6.1：0.6 日志仅证明查询前已到达，未证明 libadec 已解析或查询本身正常。新代码以当前导入槽和紧凑 OPD 检查选择全部8项有效的 libadec/cellAdec 候选；未解析则不调用。候选库实际绑定情况需本机日志确认。AAC 完整预解码并关闭后才开启 VDEC，分离初始化资源。

0.6.1 实机确认正确导出库为 cellAdec；libadec 候选的8个导入槽全部为0。此前首次AAC调用未检查绑定，这是明确的兼容错误。后续应收敛为 cellAdec 并保留调用前有效性检查；初始化资源顺序的独立影响未作对照验证。

## 0.7 分片 MP4 与有限缓冲

借鉴上游逐分片索引、异步输入存活与音频时钟的架构，新增独立的受限单轨 fMP4 解析器，未复制整个 Yo demux 实现。
每轨元数据64KB/最多128样本，检查盒长度、mdat范围、tfdt连续性、trun字段及参数集变更；输出 Annex B/ADTS 给现有固件接口。
输入包仅在 AUDONE 后复用，PCM直到硬件消费才回收；已排队到音频端口的源数据仍保留，以支持暂停/重新缓冲后从消费位置恢复。
固定测试素材仍以分块CRC核对；不把这一策略当成未知长度HTTP流方案。普通stbl MP4、多轨、B帧、seek、编辑列表及联网均未实现。
0.7 首次同时保持 AAC/VDEC 打开并增量送入，SPU资源并行、跨片段连续性和暂停/退出仍需实机验证。
